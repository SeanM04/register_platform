◎ Architecture Overview

How the v2 chatbot is structured, what changed from v1, and the design philosophy behind the tool-calling approach.

What is the UniStudio Chatbot?

UniStudio Bot is the conversational AI layer of the registrar platform at Manicaland State University of Applied Sciences (MSUAS). It gives academic staff and administrators natural-language access to live registration, performance, risk, and demographic data — without writing SQL or navigating dashboard filters.

Every answer is backed by a live database query. The bot never estimates or hallucates numbers — it calls a registered tool function which runs a real Django ORM query, then synthesises the result into a conversational reply.

ℹ️
Architecture version: v2 replaced the previous 20-handler keyword-dispatch system with LLM-driven tool calling in May 2026. The AI now decides which database functions to call rather than relying on keyword regex matching. This document covers v2 only.

Design philosophy

  • The AI is the router, not the data source. It decides which tools to call based on the user's intent and conversation history.
  • Tools are thin wrappers — they call existing Django ORM context builders. No new query logic was written; only routing changed.
  • The AI synthesises from raw JSON tool results — it is never given a pre-written answer to "rewrite conversationally" (the v1 anchor problem).
  • Resilience is non-negotiable: every AI failure falls back to a deterministic rule-based path.

Step-by-step breakdown

1

View layer — Django async view

chatbot_message_stream receives the POST, validates the JSON body, loads the ChatSession and conversation history (last 20 turns), checks the response cache, then delegates to _run_service via asyncio.to_thread so the event loop is never blocked. Status events are streamed to the browser via SSE as each processing stage completes.

2

Contextual follow-up detection

_is_contextual_reply runs before any AI call. It checks whether the message is a short affirmative or follow-up token ("yes", "sure", "go ahead", "which ones?", "show me more") and there is prior conversation history. Contextual replies bypass the greeting/out-of-scope short-circuit — they must always reach the AI with full history so the thread is maintained.

3

Lightweight intent detection

A cheap AI call (gpt-4o-mini, max 80 tokens) classifies the message into one of: greeting, out_of_scope, at_risk, demographic, data_query, general_info. Greetings and out-of-scope messages are short-circuited immediately without hitting the database. The intent is also stored in diagnostics for developer inspection.

4

Tool-calling path (primary)

When an AI provider is configured and reachable, the service runs the multi-round tool-calling exchange. It builds a 3-query lightweight scope summary, constructs a lean system prompt (no pre-loaded data), and calls _openai_tool_call_round or _google_tool_call_round. These loop for up to 4 rounds until finish_reason = "stop". See the Multi-Query Logic tab for a deep dive.

5

Rule-based fallback path

Runs when the chatbot is disabled, no provider is configured, or the tool-calling path returns no text. Builds the full scope context (8–12 DB queries), runs the 20-handler keyword dispatch to generate a fallback_reply, then optionally passes it through the legacy AI completion path for natural-language rewriting. This ensures the bot always returns a useful answer.

6

Persistence & streaming

The final reply is saved to ChatMessage (both user and assistant turns), stored in the Django response cache for identical future queries, and streamed back to the browser as a final SSE reply event. The session context cache is updated so follow-up turns can access the data without re-querying.

How _execute_tool works

When the AI returns a tool_calls array, _execute_tool(name, args, filters) dispatches each call. It maps the tool name to the appropriate context builder function, merges the AI-supplied arguments with the active topbar scope filters, runs the DB query, and returns a JSON-encoded result string.

The filters dict (year, period, faculty from the topbar) is always merged in — so if the user has "Year 2" selected in the topbar and asks "who is the top student?", the tool automatically scopes to Year 2 without the AI needing to pass it explicitly.

⟳ Multi-Round Tool Calling

How the agent chains multiple tool calls to answer compound questions — and the exact protocol used with each provider.

Why multiple rounds are necessary

Some questions cannot be answered with a single tool call. The question "who is the top student in Year 1 from the top programme?" requires the AI to:

  1. Call get_programme_statistics to find which programme has the highest pass rate
  2. Extract the programme code from the result (e.g. ACCT)
  3. Call search_top_students with programme_code="ACCT" and year_level=1

In v1, the system answered such queries by calling a single keyword handler — which either matched the wrong data or returned "I don't have that information." In v2, the AI orchestrates the calls itself and only synthesises once it has all the data it needs.

Multi-round tool-calling loop (OpenAI)
sequenceDiagram participant U as User participant S as Service participant A as OpenAI API participant D as Database U->>S: top student in Year 1 from the best programme S->>A: Round 1 - messages + tools + tool_choice auto A-->>S: finish_reason tool_calls - get_programme_statistics S->>D: _execute_tool get_programme_statistics D-->>S: ACCT pass_rate 92.2 avg 62.2 S->>A: Round 2 - messages + tool result appended A-->>S: finish_reason tool_calls - search_top_students programme_code ACCT year_level 1 S->>D: _execute_tool search_top_students ACCT year 1 D-->>S: Nyasha Calvin Muzangaza avg 72.7 S->>A: Round 3 - messages + both tool results A-->>S: finish_reason stop - final reply text S-->>U: SSE reply event streamed to browser

The loop in code

for round_num in range(4):          # max 4 rounds — prevents infinite loops
    payload = {
        "model": settings.CHATBOT_OPENAI_MODEL,
        "messages": messages,
        "tools": CHATBOT_TOOLS,
        "tool_choice": "auto",          # AI decides whether to call tools
    }
    raw = _post_openai(payload)

    finish_reason = raw["choices"][0]["finish_reason"]
    tool_calls    = raw["choices"][0]["message"].get("tool_calls") or []

    if finish_reason != "tool_calls" or not tool_calls:
        return raw["choices"][0]["message"]["content"]  # done — return text

    # Execute all tool calls from this round and append results
    messages.append(assistant_msg)
    for tc in tool_calls:
        result = _execute_tool(tc["function"]["name"], args, filters)
        messages.append({"role": "tool", "tool_call_id": tc["id"], "content": result})
    # Loop → Round N+1 — AI now has tool results and can call more or synthesise

How the AI decides which tools to call

The AI (OpenAI or Gemini) receives three inputs in every round:

  1. The system prompt — personality, tool usage rules, current scope (3 numbers), university facts
  2. Conversation history — the last N turns so it knows what was already discussed
  3. The tool schemas — descriptions and parameter types for all 8 tools

The AI's decision is driven by its tool descriptions. The compound-query rule in the system prompt reads:

"COMPOUND QUERIES — when the user's question requires multiple pieces of data,
call ALL needed tools before synthesising. Examples:
  - 'top student in year 2 from the best programme'
    → call get_programme_statistics (find the top programme),
      THEN call search_top_students with that programme_code and year_level=2.

You may issue multiple tool calls in a single response — do so whenever you need
more than one dataset to fully answer the question. Do NOT synthesise until you
have all the data."
⚠️
Parallel vs sequential tool calls: OpenAI can return multiple tool calls in a single round (parallel calling). This means for some compound queries the AI may call both get_programme_statistics AND search_top_students simultaneously in Round 1 if it already knows the programme code. The loop handles both patterns — it processes all tool calls in the array before proceeding to the next round.

☁️ AI Providers

OpenAI and Google Gemini are both supported. The active provider is controlled from System Management and read from the database at runtime.

OpenAI

  • Model: gpt-4o-mini (default, configurable via CHATBOT_OPENAI_MODEL)
  • Intent detection: always gpt-4o-mini (hardcoded, fast)
  • Tool calling: tools array + tool_choice: "auto"
  • Multi-round: loop on finish_reason == "tool_calls"
  • Tool result role: "tool" with tool_call_id
  • Max tokens: 800 per round

Google Gemini

  • Model: gemini-2.5-flash-lite (default, configurable)
  • Tool calling: functionDeclarations (types uppercased via _upcase())
  • Multi-round: loop on functionCall in response parts
  • Tool result role: functionResponse part in a user turn
  • History: mapped from OpenAI format (user/assistant) to Gemini format

Provider selection — how it works

The active provider is determined at request time by get_chatbot_provider_status(). It reads from the database first (PlatformSetting.get_value("ai_provider")), then falls back to the static CHATBOT_PROVIDER setting. This means changing the provider in System Management takes effect immediately without a server restart.

def get_chatbot_provider_status() -> dict:
    # 1. Read from DB (System Management sets this)
    db_provider = PlatformSetting.get_value("ai_provider", "").strip().lower()
    # 2. Fall back to static setting if DB has no value
    provider = db_provider or settings.CHATBOT_PROVIDER
    # 3. Resolve: "openai", "google", "auto", or "rules"
    return {
        "provider":      provider,
        "openai_ready":  provider in ("openai", "auto") and bool(settings.OPENAI_API_KEY),
        "google_ready":  provider in ("google", "auto") and bool(settings.GOOGLE_API_KEY),
        "ai_available":  openai_ready or google_ready,
        "enabled":       settings.CHATBOT_ENABLED,
    }
ℹ️
Provider priority when set to "auto": OpenAI is checked first, then Google Gemini. In practice, set an explicit provider in System Management for predictable behaviour. The "auto" mode is intended for development environments where only one key may be present.

Google API format conversion

Google Gemini requires type strings in uppercase (STRING, INTEGER, ARRAY, OBJECT) and uses a different message structure. The _upcase() helper and the Google round function handle this transparently.

# OpenAI format (stored in CHATBOT_TOOLS)
{ "type": "function", "function": { "name": "search_top_students",
  "parameters": { "type": "object", "properties": {
    "count": { "type": "integer" } } } } }

# Google format (converted by _upcase() at request time)
{ "functionDeclarations": [{ "name": "search_top_students",
  "parameters": { "type": "OBJECT", "properties": {
    "count": { "type": "INTEGER" } } } }] }

🧠 Session & Context

How conversation state is preserved across turns, how follow-up replies are detected, and how the scope filters flow through the system.

In-process session context cache

An in-memory Python dict (_SESSION_CONTEXT) keyed by Django session key stores the last tool result for each active session. Entries expire after 2 hours (TTL). Expired entries are pruned on every write.

This allows follow-up turns to access the previous tool result without re-querying the database — the AI can reference the data from the prior round when a user says "tell me more about that".

⚠️
Production limitation: The dict is per-process. With multiple Gunicorn workers, each worker has its own cache. Upgrade to Redis for multi-worker deployments: cache.set(f"chat_ctx:{session_id}", data, timeout=7200).

Conversation history window

The last 20 turns of the conversation (HISTORY_WINDOW = 20) are loaded from ChatMessage on each request. They are sent to the AI as real multi-turn messages (user / assistant roles), not embedded in the system prompt.

History is filtered in _build_openai_messages — only user and assistant roles pass through, each truncated to 400 characters. This prevents token overflow on long sessions.

Contextual follow-up detection — _is_contextual_reply

Before any AI call, the service checks if the current message is a short follow-up to the previous assistant turn. The detection logic:

  1. Message is short (≤6 tokens when split by whitespace)
  2. All tokens are in the _FOLLOWUP_TOKENS frozenset: yes, yeah, sure, ok, show, more, continue, which, those, tell, go, ahead, details, elaborate, and, also…
  3. There is at least one prior turn in the history

If all three conditions pass, is_contextual = True. This flag prevents greeting/out-of-scope short-circuits — a "yes" is never intercepted and returned as a greeting reply. It also overrides the fallback_reply on the rule-based path so the AI can't anchor to a scope summary.

Scope filters — how topbar selection flows through

The topbar filters (year, period, faculty) are sent with every chat message from the client. They flow through the entire chain:

Client JSON → filters dict → _normalize_filters() → _base_registrations(filters)
  └── _apply_scope_filters(queryset, filters)
        ├── period__name__icontains = filters["year"]   # e.g. "1" matches "Semester 1"
        ├── period__name__icontains = filters["period"] # exact period label
        └── programme__department__faculty__name = filters["faculty"]

Every tool call inherits the topbar filters — when the AI calls search_top_students, it automatically runs within the user's selected year/period/faculty. The AI can layer additional filters on top (e.g. year_level=2 from the query), but it cannot escape the topbar scope.

The 20 keyword handlers

The rule-based path runs the message through a chain of handlers. Each returns a string if it fires, or None to pass to the next handler. The chain is defined in _REPLY_HANDLERS:

_REPLY_HANDLERS = [
    _reply_risk_summary,        # "at risk", "watchlist", "failing"
    _reply_decisions,           # "repeat", "discontinue", "deferred"
    _reply_top_student,         # "top student", "best performer", "top 5 students"
    _reply_demographics,        # "gender", "demographic", "year distribution" (guards _is_top_student_query)
    _reply_period_performance,  # month/semester name in message
    _reply_course_difficulty,   # "hardest", "easiest", "course rank"
    _reply_student_profile,     # registration number pattern (M2018P)
    _reply_programme_profile,   # programme name/code match
    _reply_faculty_profile,     # faculty name match
    _reply_course_profile,      # course code pattern (ACCT301)
    _reply_completion_rules,    # "carry", "complete", "graduate", "requirements"
    _reply_admissions,          # "apply", "admission", "entry requirements"
    _reply_graduation,          # "graduation", "ceremony"
    _reply_default,             # always fires — scope summary
]
✅
Why keep the fallback? The tool-calling path requires a live AI API call. Network timeouts, API outages, rate limits, or misconfigured keys all cause failures. The rule-based path ensures the bot never returns a blank response — it degrades gracefully to deterministic keyword matching.

Diagnostics — tracking what happened

Every reply includes a diagnostics dict that tells developers exactly which path was taken:

Known limitations & next improvements

  1. In-process session cache — does not survive server restarts or work across multiple Gunicorn workers. Replace with Redis (django.core.cache) for production multi-worker deployments.
  2. Two AI round trips per query — the tool-calling path makes at least 2 API calls (intent detection + tool round). Simple factual queries could use a fast-path that skips intent detection.
  3. History token overflow — long sessions (30+ turns) will cause older turns to be silently truncated. A sliding summary approach would be more robust.
  4. No compare_years tool — queries like "compare Year 1 vs Year 3 pass rates" fall back to get_demographic_breakdown, which is approximate. A dedicated comparison tool would close this gap.

BUG-01 — Invalid OpenAI model name caused HTTP 400 on every request

SymptomAll chatbot questions fell through to rule-based replies. Terminal showed OpenAI tool-call pass 1 failed: HTTP Error 400: Bad Request followed by Chatbot provider request failed: HTTP Error 400.
Root cause.env had OPENAI_INSIGHTS_MODEL= gpt-5.4-mini — a fabricated model name with a leading space. OpenAI returns 400 for any unrecognised model ID. settings.py also hardcoded the same bad default.
Why intent workedIntent detection hardcodes gpt-4o-mini directly and never reads CHATBOT_OPENAI_MODEL, so it continued to function while everything else failed silently.
 
# .env — before
OPENAI_INSIGHTS_MODEL= gpt-5.4-mini   # invalid model, leading space

# .env — after
OPENAI_INSIGHTS_MODEL=gpt-4o-mini     # valid model, no space

# settings.py — before
OPENAI_INSIGHTS_MODEL = os.getenv("OPENAI_INSIGHTS_MODEL", "gpt-5.4-mini")
CHATBOT_OPENAI_MODEL  = os.getenv("CHATBOT_OPENAI_MODEL", OPENAI_INSIGHTS_MODEL)

# settings.py — after (fixed default + .strip() on both lines)
OPENAI_INSIGHTS_MODEL = os.getenv("OPENAI_INSIGHTS_MODEL", "gpt-4o-mini").strip()
CHATBOT_OPENAI_MODEL  = os.getenv("CHATBOT_OPENAI_MODEL", OPENAI_INSIGHTS_MODEL).strip()

BUG-02 — Programme code filter silently dropped, returning wrong student

Symptom"Who is the top student in Year 1 from the top programme?" returned Tamia Tambudzai Gwarada (THMA) — but the answer said they were from ACCT. Programme in the profile contradicted the programme in the headline.
Root causeIn _execute_tool, the AI-supplied programme_code="ACCT" was only appended to a fake message string ("top 5 students ACCT"). _build_top_student_context only parsed year numbers from the message — it never parsed programme codes. The filter was silently ignored and the query ran across all programmes, returning whoever had the highest average mark globally.
Verified withDirect DB query confirmed Nyasha Calvin Muzangaza (M2018P, avg 72.7) is the correct top Year 1 ACCT student.
 
# _build_top_student_context — before (no programme_code param)

# _build_top_student_context — after (programme_code as real DB filter)

BUG-04 — "top 5 students" not recognised as a top-student query

Symptom"Give me the top 5 students in Year 2" returned "I don't have individual student data."
Root cause_is_top_student_query matched phrases like "top student" (singular) but not "top 5 students" (number + plural). The numeric pattern was missing from detection.
 
# Two new regex patterns added after _TOP_STUDENT_SIGNAL_KWS
_TOP_STUDENT_N_RE = re.compile(
    r"\b(top|best|highest)\s+\d*\s*students?\b", re.IGNORECASE
)
_TOP_N_COUNT_RE = re.compile(
    r"\b(top|best|highest)\s+(\d+)\s*students?\b", re.IGNORECASE
)

# _is_top_student_query — before (only keywords, no numeric pattern)
def _is_top_student_query(msg_lower):
    return any(kw in msg_lower for kw in _TOP_STUDENT_KWS)

# _is_top_student_query — after (keywords + numeric regex)
def _is_top_student_query(msg_lower):
    if any(kw in msg_lower for kw in _TOP_STUDENT_KWS): return True
    if _TOP_STUDENT_N_RE.search(msg_lower): return True
    return False

BUG-05 — "yes" follow-up returned scope summary instead of the offered data

SymptomAfter the bot offered "Would you like a detailed profile for [student]?", the user replied "yes" and received an unrelated scope summary.
Root causeEvery turn called _build_rule_based_reply → _reply_default → scope summary. This became the fallback_reply injected into the system prompt as "Baseline answer: rewrite conversationally". The AI rewrote the scope summary instead of acting on the previous offer.
FixWhen is_contextual=True: (1) override fallback_reply with a history-guidance string that explicitly instructs the AI not to re-summarise scope; (2) run _extract_regnum_from_history to recover a student registration number from the previous turn and inject it as a student target so the AI has real data to work with.
 
# New helper — recovers regnum from last assistant turn
def _extract_regnum_from_history(history):
    for turn in reversed(history or []):
        if turn.get("role") == "assistant":
            match = REGNUM_PATTERN.search(turn.get("content", ""))
            if match: return match.group(0)
    return None

# get_chatbot_reply — contextual path override
if is_contextual:
    prev_regnum = _extract_regnum_from_history(history)
    if prev_regnum and not context.get("student_targets"):

        if recovered:
            context["student_targets"] = [recovered]
    fallback_reply = (
        "This is a follow-up to the previous answer. "
        "Do NOT re-summarise overall scope data. "
        "Use the conversation history to determine exactly what the user is affirming..."
    )

BUG-06 — Compound query returned partial answer after one tool round

Symptom"Who is the top student in Year 1 from the top programme?" returned programme statistics (ACCT pass rate) but said "I don't have access to individual student rankings."
Root causeThe old tool-calling implementation was a fixed two-pass exchange: Pass 1 collected tool calls, executed them, and passed results to Pass 2 for synthesis. Pass 2 had no tools available, so when it needed a second DB call (to fetch students from ACCT), it couldn't make one and had to give up.
FixConverted to a multi-round loop (max 4 rounds). Each round checks finish_reason: if "tool_calls", execute the tools and continue; if "stop", return the final text. The AI now orchestrates all the tool calls it needs before synthesising.
 
# Before — fixed two-pass (Pass 2 had no tools)
raw1 = post(payload_with_tools)      # Pass 1
execute_tools(raw1.tool_calls)
raw2 = post(payload_no_tools)        # Pass 2 — synthesise only
return raw2.text

# After — multi-round loop (tools available every round)
for round_num in range(4):
    raw = post(payload_with_tools)
    if raw.finish_reason != "tool_calls":
        return raw.text              # done
    execute_tools(raw.tool_calls)   # loop → next round

Architecture Improvements

IMP-01 — Replaced 20-handler keyword dispatch with 8-tool AI routing

The entire primary request path was rewritten. Instead of building 8–12 DB queries upfront and running a keyword-handler chain, the AI now receives a lean system prompt and 8 registered tool schemas. It selects which tools to call based on the user's intent and conversation history.

Files changed: services/chatbot_service.py — added CHATBOT_TOOLS constant, _execute_tool, _build_tool_system_text, _openai_tool_call_round, _google_tool_call_round.

IMP-02 — Added in-process session context cache

A threading.Lock-protected dict (_SESSION_CONTEXT) keyed by Django session key stores the last tool result and active filters per user session. TTL is 2 hours. The cache is written after every successful tool-calling reply and consulted on follow-up turns.

Files changed: services/chatbot_service.py — _SESSION_CONTEXT, _get_session_ctx, _store_session_ctx. chatbot/views.py — session_id parameter wired through _call_service, _run_service, and the SSE stream task.

IMP-03 — Added compound-query instruction to the tool system prompt

An explicit compound-query rule was added to _build_tool_system_text. The AI is now instructed to call all tools needed to fully answer a question before synthesising — with worked examples of multi-tool chains. This resolved BUG-06 at the prompt level, and the multi-round loop (BUG-06 code fix) handles cases where the AI needs intermediate results before it can decide the next call.

IMP-04 — Lightweight scope summary replaces full context build on tool path

The tool-calling path uses _build_lightweight_scope_summary (3 DB queries: student count, result count, average mark) instead of the full _build_scope_context (8–12 queries). This reduces DB load significantly for the common case where the AI needs targeted data, not a full dump.
