💡 Why It Matters

How the chatbot saves time and improves decisions for registrar staff and academic management.

⏱️

Faster answers Staff get student risk profiles, pass rates, and decision breakdowns in seconds — without running a report or waiting for IT.

📊

Always live data Every answer comes from the current database scope. No stale exports, no manual pulling — the numbers are always up-to-date.

🔒

Secure by default Only authenticated users can access the chatbot. Scope filters (year, period, faculty) are enforced on every query — staff only see what they're allowed to see.

🌐

No AI cost required The chatbot works fully in Guidance mode with no API subscription. AI enrichment is optional and can be switched on when a key is available.

📱

Zero training needed Staff ask questions in plain language — "Who is failing in Engineering this semester?" — and get a structured answer immediately.

🔧

Extensible by developers New question categories can be added without touching the frontend or changing the database schema — just add a branch in the service file.

⚡ Two Operating Modes

The chatbot works with or without an AI API key configured.

🤖 AI Mode

  • Google Gemini (primary) or OpenAI (fallback) configured via API key
  • Live scoped DB data sent as grounding context
  • Deterministic baseline answer always computed first
  • AI enriches, explains, and contextualises the answer
  • Status indicator shows "Google Gemini" or "OpenAI" in the chat header

📐 Guidance Mode

  • No API key required — works fully offline from the DB
  • Every analytical question still returns a real answer from live data
  • Rule-based replies are identical to the AI baseline — just without enrichment
  • Identical questions are cached for 1 hour to skip re-computation
  • Status indicator shows "Guidance mode" in the chat header

🌐 Browser Layer

The FAB (floating action button) in the bottom-right corner opens the chat panel. All UI logic lives in chatbot.js — no page reload needed. Messages are sent via fetch() with the CSRF token attached.

🐍 Django Platform

chatbot/views.py handles authentication, session management, and caching. It delegates all analytics to chatbot_service.py — the view itself never queries the ORM directly for data.

🗄️ Data Layer

The service queries Student, Registration, and CourseResult via the Django ORM — the same models used by every other dashboard page. Completion and risk logic is imported from authoritative service files, not duplicated.

🤖 AI Providers (optional)

Google Gemini is tried first, OpenAI second, rule-based fallback third. The chatbot is fully functional with no API key configured — AI enriches answers but never replaces the live database data.

⚙️ Master Switch

CHATBOT_ENABLED in settings.py is the top-level gate. Set it to False to hide the widget entirely across the whole platform — no API key needed, no UI rendered.

✅ Gemini First

If GOOGLE_API_KEY is configured, Google Gemini is called first. The response is only accepted if it is non-empty. An HTTP timeout or connection error automatically triggers the fallback — no crash, no user-visible error.

🔄 OpenAI Fallback

If Gemini is not configured or its response is empty, OpenAI is tried next. The same acceptance logic applies — non-empty response wins, any failure drops to the rules engine.

📋 Rules Always Work

The rule-based engine is never skipped — it computes a deterministic answer from live database data regardless of AI availability. When AI is configured, this baseline answer is passed to the AI as grounding context.

Context Building — What Gets Queried Per Message
flowchart LR MSG["User message"] MSG --> SC["_summarize_scope\nalways runs"] MSG --> STU["_build_student_context\nif reg-number found"] MSG --> PROG["_build_programme_context\nif programme named"] MSG --> FAC["_build_faculty_context\nif faculty named"] MSG --> COURSE["_build_course_context\nif course code found"] MSG --> RISK["_build_at_risk_context\nif risk keyword"] MSG --> DIFF["_build_course_difficulty_context\nif hardest/easiest keyword"] MSG --> PER["_build_period_performance_context\nif period name detected"]

📊 Always Runs: Scope Summary

_summarize_scope() fires on every single message. Returns totals, pass rate, median mark, gender breakdown (with counts and percentages), watchlist counts, proceeding count/pct, at_risk_pct, and the top faculties, programmes, and decisions — giving every reply a rich live baseline.

🎓 Student Lookup (conditional)

Triggered only when the message contains a registration number pattern (e.g. M22ABC). Pulls the full student profile: all marks, classification, risk score, per-period completion percentage (with zero_reason and working formula fields), and graduation status.

⚠️ At-Risk Context (conditional)

Triggered by keywords like risk, watchlist, or failing. Queries candidates with adverse decisions or carrying status, scores each one, and returns the top 10 with band counts (moderate / high / critical).

📚 Course Difficulty (conditional)

Triggered by hardest, easiest, or difficult. Aggregates CourseResult records per course (minimum 5 students), then returns the 8 hardest and 8 easiest courses ranked by average mark.

🏛️ Programme / Faculty / Course (conditional)

_build_programme_context (now includes fail_rate and carrying_count), _build_faculty_context, and _build_course_context each run only when the message names a matching entity. This keeps every response fast — expensive queries are never run unless the message warrants them.

📅 Period Performance (conditional)

_build_period_performance_context() activates when the message names a specific academic period (e.g. "August 2025" or "Semester 1"). Returns per-period totals, average mark, pass/fail rate, decision distribution, and a breakdown by programme — mirroring the prototype's full period analytics tool.

🧱 5-Layer Architecture

The chatbot is built in five discrete layers, each with a single responsibility. They are independently testable and degrade gracefully — removing an optional component (e.g. AI providers) never breaks the layers below it.

Layer 1 — Browser UI

chatbot.js and chatbot.css form the entire front-end. The FAB (floating action button) in the bottom-right corner toggles the panel. The textarea auto-expands as the user types (up to ~6 lines) via the _autoGrow() function. Message history is stored in sessionStorage for instant re-render on panel open — the authoritative copy lives in ChatMessage rows in the database.

Layer 5 — Safety and Cache

Every request is authenticated via @ajax_login_required and validated for CSRF. ChatResponseCache short-circuits identical rule-based queries within a 1-hour window. SENSITIVE_PATTERNS blocks injection, jailbreak, and credential-extraction attempts before any database query or AI call runs.

Layer 2 — Intent Detection

A dedicated lightweight AI call (max 80 tokens, 5 s timeout, temperature 0) classifies the message into one of 11 intents and extracts entities — registration number, programme codes, period, faculty, risk band. Greeting and out_of_scope are returned immediately with no database query. Any failure silently falls back to general_info.

Layer 3 — Context Engine

_summarize_scope() always runs, giving every reply live scoped data as a baseline (now including median mark, proceeding count/pct, at_risk_pct, and gender percentages). Seven additional context builders fire conditionally based on the intent and entities detected in Layer 2. _build_rule_based_reply() dispatches across 18 named branches to produce a deterministic, grounded answer.

Layer 4 — Data

All queries use the same Django ORM models as the rest of the dashboard — Student, Registration, CourseResult, Programme, Faculty. Completion percentage and risk scoring are imported directly from completion_rules.py and risk/constants.py — never duplicated in the chatbot service.

AI Providers — optional

Google Gemini handles both the intent call and the full reply when configured. OpenAI uses gpt-4o-mini via the Chat Completions API for intent, and the configured main model via the Chat Completions API (/v1/chat/completions) for the full multi-turn reply. If neither is configured, the rule-based reply from Layer 3 is returned directly — the platform is fully functional without any API key.

Zero-DB Short-Circuits

When intent is greeting or out_of_scope, the function returns immediately after the intent call — _build_scope_context() is never called. This saves 5–10 database queries per greeting message and keeps response time under 100 ms for those cases.

Graceful Fallback Chain

If the intent detection call fails for any reason (timeout, malformed JSON, HTTP error), the service silently falls back to "general_info" and continues. The keyword-based branches in _build_rule_based_reply() also catch greetings and out-of-scope questions as a secondary net when no AI key is configured.

CACHEABLE_INTENTS

Intents whose rule-based replies contain no personal student data are marked cacheable: data_query, admissions, general_info, comparison, demographic, decision_analysis, calculation. Student-specific replies (student_lookup, at_risk) are never cached — data freshness is critical for those.

Entity Extraction

Alongside the intent, the AI extracts five structured entities: registration number (regnum), programme codes (e.g. ACCT, BMAN, INSY), the named academic period, faculty name, and risk band. These are stored on the context dict as _intent_entities and passed through to the AI's full reply prompt.

Why a Separate Intent Call?

The intent call is distinct from the main reply call. It uses temperature 0 and a hard 80-token cap — it needs to return only a small JSON object, not prose. This keeps it fast (typically 200–400 ms) and cheap. The main reply call that follows uses the full context window and higher token limits.

Why gpt-4o-mini for OpenAI Intent?

The intent call always uses gpt-4o-mini regardless of CHATBOT_OPENAI_MODEL. This is intentional: intent classification is a structured extraction task where a small, fast model outperforms a large reasoning model. The main reply uses whatever model is configured in settings.

Why Chat Completions for both Intent and Reply?

Both the intent call and the main reply now use the OpenAI Chat Completions API (/v1/chat/completions). Chat Completions supports the full messages array needed for multi-turn conversation history — the previous Responses API did not support this, so the migration was necessary to enable contextual follow-up replies.

🔄 Request Flow

Step-by-step lifecycle of a single user message from browser to response.

1️⃣ Optimistic UI

The moment the user hits Send, chatbot.js immediately shows the user's message and the animated typing dots — before any server response. The input is disabled to prevent double-sends while the request is in-flight.

2️⃣ Session & Auth Gate

Every request passes through @ajax_login_required. The view creates or retrieves a ChatSession tied to the browser session key, then loads the last 16 messages as the AI conversation history window.

3️⃣ Response Cache (1 hour)

Before hitting the service, the view checks ChatResponseCache using an MD5 hash of the message text. If a matching rule-based reply exists and is less than 1 hour old, it is returned immediately — no DB analytics queries run.

4️⃣ Safety Gate & Intent Detection

The service normalises scope filters, then runs SENSITIVE_PATTERNS regex checks. If the message is safe and an AI provider is configured, _detect_intent() fires — an 80-token call that classifies the message into one of 11 intents. Greeting and out_of_scope are returned immediately with no database query at all.

5️⃣ Persist & Cache

After the reply is produced, the view writes both the user turn and the assistant turn to ChatMessage in a single bulk_create call. Only rule-based replies (source == "rules") are written to the response cache — AI and per-student replies are never cached.

6️⃣ Source Badge

The JSON response includes a source field: google, openai, rules, or cache. The chat widget uses this to display a labelled badge on AI-sourced replies and to update the status indicator in the chat header.

How the three chatbot tables relate to each other and to the Django auth user.

Entity Relationship Diagram

🔑 ChatSession

One row per browser session per user, keyed on Django's request.session.session_key. Created automatically on the user's first message. The user FK is nullable — sessions can exist before a user is associated.

💬 ChatMessage

One row per turn — user and assistant messages stored as separate rows with a role field ("user" or "assistant"). The view loads the last 16 rows as the AI's conversation history window.

⚡ ChatResponseCache

MD5-keyed cache for rule-based replies. TTL is 1 hour (expires_at). The same cache entry is shared across all users asking identical questions. Only source == "rules" replies are cached — AI and per-student replies are never cached.

⚠️ Known Limitations

Constraints developers and administrators should be aware of.

🔍

Response cache is shared across users. Two different staff members asking the same rule-based question within the same 1-hour window receive the same cached reply. This is intentional for performance, but means per-user personalisation is not applied to cached responses.

⏱️ 15-second AI timeout

CHATBOT_TIMEOUT_SECONDS = 15. If the AI provider does not respond within 15 seconds, the service automatically falls back to the rule-based reply. The user sees a valid answer, but the source badge will show "Guidance" instead of "Google Gemini".

💬 16-message history window

The AI receives only the last 16 messages (8 turns) as conversation history. Older messages in the session are not sent to the AI, though they remain stored in ChatMessage rows in the database.

✂️ 1200-character input limit

The textarea enforces maxlength="1200" on the client. The server also truncates to MAX_MESSAGE_LENGTH before processing. Very long questions are silently truncated — the user is not warned.

🗄️ Cache is not scope-aware

The MD5 cache key is computed from the message text only — not from the active scope filters (year, period, faculty). If a user changes the topbar filters and asks the same question, they may receive a cached reply from the previous scope if it was cached within the last hour.

🧪 Local Development & Testing

How to run and test the chatbot without an AI key configured.

ℹ️

In Guidance mode (no API key) the chatbot still answers every analytical question using live database data. This is the fastest way to test new reply branches without incurring AI API costs.

1. Run with no AI key

Leave GOOGLE_API_KEY and OPENAI_API_KEY empty in your .env file. The service will route directly to the rule-based engine. Every branch in _build_rule_based_reply can be tested this way.

2. Test a specific branch

Send a message that matches the trigger keywords for the branch you added. Check the source field in the JSON response — it should be "rules". The diagnostics object shows which context functions ran.

3. Clear the cache during testing

Rule-based replies are cached for 1 hour. During development, click "New conversation" in the chat panel or call POST /api/chatbot/clear/ to clear the session. To clear the response cache entirely, use the Django admin → ChatResponseCache → purge_expired action.

4. Standalone prototype

For testing prompt changes without the full Django stack, use the standalone terminal prototype at registrar_platform/unistudio_chatbot.py. Run it with python unistudio_chatbot.py. It uses SQLite and does not require a running server.

🔒 Security Controls

Layers of protection applied on every request.

🔐

Authentication

@ajax_login_required decorator on both endpoints. Unauthenticated requests receive HTTP 401.

🛡️

CSRF Protection

X-CSRFToken header sent with every fetch request. Validated by Django's middleware.

✂️

Input Length Limit

maxlength="1200" on the textarea. Server truncates to MAX_MESSAGE_LENGTH before any processing.

🚫

Injection & Jailbreak Gate

SENSITIVE_PATTERNS regex blocks credential requests, prompt injection, and instruction-override attacks before any DB query.

🔑

API Key Protection

Keys read from environment variables — never embedded in code, templates, or version control.

🔭

Scope Enforcement

All DB queries respect the topbar filters (year / period / faculty) — the same scope enforced across the rest of the platform.

🔧 How to Extend

➕

Add a reply branch

Add keyword detection in _build_rule_based_reply. For new DB data, add a _build_*_context() function and call it conditionally in _build_scope_context — only when message keywords warrant the extra query.

🤖

Add an AI provider

Add a _request_<provider>_chatbot_response(system_text, history, user_turn) function that builds the provider's multi-turn payload, a <provider>_ready flag in get_chatbot_provider_status(), and insert the provider into the routing chain in get_chatbot_reply().

💬

Change suggestion chips

Update the suggestions list inside the chatbot_bootstrap context dictionary in dashboard/views.py. Chips are shown only before the first message in a session.

🚫

Disable on a specific page

Pass chatbot_enabled=False in the page view's context. The base template checks chatbot_bootstrap.enabled before rendering the widget HTML or loading the JS file.
